# 阶段三：多功能场景 3 与项目级 DSL 门禁

## 1. 阶段目标

在用户确认最新 chunks 结果后，允许从功能清单逐个、重复执行场景 3；当全部功能至少发起过一次建模后，调用现有 `query-requirement-dsl-artifacts`，用最新结构化结果和人工审核共同决定是否进入流水线三。

本阶段不实施场景 7、8、9。

## 2. 前置条件

- 用户已确认阶段二人工验收通过。
- 当前对话存在最新成功 chunks payload。
- payload 至少包含一个 `functional_requirement`。
- 用户已点击“确定条目化结果，进入功能建模”。

## 3. 场景 3 表单

### 3.1 字段

| 字段 | 来源 | 是否可编辑 |
| --- | --- | --- |
| 功能分块 ID | 所选 chunk 的 `chunk_id` | 否 |
| 功能名称 | `canonical_function_name`、`title`、`chunk_id` 依次回退 | 否 |
| 功能 Markdown | 安全拼接路径或用户手工输入 | 是 |
| 项目根目录 | 最新成功 chunks 的 `project_root` | 是，但修改时提示会影响 DSL 查询范围 |
| 补充要求 | 用户输入 | 是 |

没有选中功能时显示功能清单引导，不显示可提交空表单。功能 Markdown 或项目根目录为空时禁止发送。

### 3.2 固定提示词

发送文本固定为：

```text
请使用 requirement_analysis_pipeline 对一个功能进行完整建模。
功能分块 ID：<chunk_id>
功能名称：<功能名称>
功能 Markdown：<功能 Markdown 绝对路径>
项目根目录：<项目根目录>
目标：生成实体、条件逻辑、四类 DSL、DSL 对齐结果和测试用例。
要求：从本功能原文中增量维护项目关系；只有原文唯一确定的内容才可写回 DSL；
不得修改原始需求 Markdown；DSL 语法或对齐失败时停止测试用例生成并报告原因。
补充要求：<用户内容，仅非空时添加>
```

`功能分块 ID` 和 `功能名称` 是前端恢复映射所需的稳定可见字段，不改变 Agent 的输入文件和输出协议。

### 3.3 发送行为

- 调用现有 ConversationWorkspace `onSend`。
- 发送成功后清空补充要求，保留功能选择和路径，方便用户查看或重新建模。
- 用户可立即选择下一功能，但 Assistant 生成期间禁止再次发送任何场景表单或 Skill 请求。
- 自由聊天仍可在非生成状态使用，不自动改变功能进度。

## 4. 功能进度推导

### 4.1 识别场景 3 消息

只识别同时满足以下条件的用户文本：

- 包含固定首行 `请使用 requirement_analysis_pipeline 对一个功能进行完整建模。`；
- 存在非空 `功能分块 ID：`；
- 存在非空 `功能 Markdown：`；
- 消息位置晚于当前采用的最新成功 chunks block。

按消息顺序为每个 `chunk_id` 保存最近一次场景 3 消息位置。不得用自然语言回复判断建模成功。

### 4.2 展示状态

- 当前 chunks 中没有对应场景 3 消息：`待建模`。
- 有一次对应消息：`已发起`。
- 有两次或更多对应消息：`已重新建模`。
- 消息中的 chunk ID 不在当前最新 chunks：归入“历史或未知功能”，不计入当前覆盖率。

同一个 chunk 只占一个清单项；覆盖数为当前 chunks 中至少有一次场景 3 消息的不同 chunk ID 数量。

### 4.3 chunks 更新

如果用户重新执行场景 1 并获得更新后的成功 chunks：

- 之前 chunks 对应的场景 3 消息不计入新清单；
- 新清单从最新 chunks block 后的消息重新计算；
- 工作流返回流水线一审核状态；
- 旧 DSL 查询结果全部失效。

## 5. 项目级 DSL 查询

### 5.1 启用条件

“查询项目 DSL 产物”按钮仅在以下条件全部满足时启用：

- 当前 chunks 功能数大于零；
- 当前功能覆盖数等于功能总数；
- 所有场景 3 消息采用同一个项目根目录；
- 当前没有生成中的回复；
- 当前对话可发送。

项目根目录不一致时列出涉及的功能，不自动选择其中一个。

### 5.2 Skill 调用模板

```text
请使用 $query-requirement-dsl-artifacts 查询以下项目根目录中已生成的需求 DSL 产物。
项目根目录：<项目根目录>
请将完整结构化结果保留在工具结果中，最终回答只显示 Skill 规定的统计信息。
```

前端只发送文本，不直接执行 ZIP 中的 Python 脚本。

### 5.3 最新 DSL 证据

按消息顺序执行：

1. 找到当前 chunks 下所有功能的最近一次场景 3 消息位置。
2. 取这些位置中的最大值，作为最新建模变更点。
3. 只检查变更点之后的 `$query-requirement-dsl-artifacts` 工具面板。
4. 选择最新一个由现有 handler 匹配和解析的面板。
5. 只有 `payload.state === "success"` 才进入 DSL 审核状态。
6. `loading`、`parse-error`、`remote-error` 或没有面板时均保持当前阶段，并允许重新查询。

任一功能再次发送场景 3 后，最大变更点后移，旧 DSL 结果自然失效。

## 6. DSL 覆盖核对

从成功 payload 读取：

- `summary.feature_count`
- `summary.requirement_count`
- `summary.artifact_count`
- `summary.empty_artifact_requirement_count`
- `summary.metadata_missing_count`
- `warnings`

自动门禁只比较：

```text
summary.feature_count === 当前 functional chunk 数量
```

展示以下信息供人工审核：

- chunks 功能数；
- DSL 功能数；
- 需求数、DSL 数、映射数；
- 无产物需求数；
- 元数据缺失数；
- Skill warnings 数量。

如果功能数不一致：

- 显示明确差异；
- 禁用“确定全部功能 DSL 已审核”；
- 不扫描目录、不修改 Skill 结果、不提供自动忽略按钮；
- 用户必须重新建模、重新条目化或修正项目输入后再查询。

功能数一致不代表 DSL 语法、对齐和测试用例自动通过，因此仍必须由用户审核现有 DSL 卡片后确认。

## 7. 进入流水线三

“确定全部功能 DSL 已审核”仅在以下条件满足时启用：

- 最新 DSL payload 为 success；
- `feature_count` 与当前功能数一致；
- 当前没有更新的场景 3 消息；
- 当前不在生成状态。

点击确认后：

- 本地工作流显示流水线二 completed、流水线三 active；
- 展示阶段四将实现的场景 7 占位区；
- 不发送自动确认消息，不自动生成 TTL，不自动连接 GraphDB。

如果刷新发生在确认后但场景 7 尚未发送，用户需要再次确认。场景 7 一旦发送，后续阶段可从其固定提示词恢复。

## 8. 本阶段不得实施

- 不把“已发起”显示为“建模成功”。
- 不用 `conversationStatus=completed` 证明功能完成。
- 不修改 DSL handler 的协议、payload 或卡片编辑能力。
- 不自动并发发送多个场景 3。
- 不调用 GraphDB 或本体 Skill。
- 不新增项目级持久化进度。

## 9. 阶段交付与停止

完成代码修改后：

1. 只检查本次改动范围和差异。
2. 不运行自动构建或测试。
3. 提交阶段报告，引用 C 组、D 组、F04-F05。
4. 明确停止，等待用户人工确认后再进入阶段四。
